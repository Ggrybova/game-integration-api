# Decisions

- EN: Standard library only for routing (net/http ServeMux with method patterns, Go 1.22+) and logging (log/slog): no external dependencies for these.
- UA: Лише стандартна бібліотека для роутингу (net/http ServeMux з методами в шаблонах, Go 1.22+) і логів (log/slog): жодних зовнішніх залежностей для цього.

- EN: The schema and seed are plain SQL files run by the Postgres image from /docker-entrypoint-initdb.d on the first start with an empty volume. There is one schema that does not evolve, so a migration tool adds code without benefit; docker compose down -v resets the state (assignment 5.1). In production I would use versioned migrations (e.g. golang-migrate) as a separate step before deploy.
- UA: Схема і seed — звичайні SQL-файли, які образ Postgres виконує з /docker-entrypoint-initdb.d при першому старті з порожнім volume. Схема одна й не змінюється, тож інструмент міграцій додав би код без користі; docker compose down -v скидає стан (завдання 5.1). У production я б використала версіоновані міграції (наприклад, golang-migrate) окремим кроком перед деплоєм.

- EN: Configuration lives in .env (not in git); .env.example is copied once with cp .env.example .env before docker compose up. No defaults are hidden in docker-compose.yml.
- UA: Конфігурація живе в .env (не в git); .env.example копіюється один раз командою cp .env.example .env перед docker compose up. У docker-compose.yml немає прихованих значень за замовчуванням.

- EN: The Wallet API key is not written in code: the service reads it from WALLET_API_KEY. The key is public and valid only for the mock (assignment 5.1), so .env.example holds it, labelled as the mock key.
- UA: Ключ Wallet API не записано в коді: сервіс читає його з WALLET_API_KEY. Ключ публічний і діє лише для mock (завдання 5.1), тому .env.example містить його з позначкою, що це ключ mock.

- EN: After a Wallet restart its balances are accepted as they are (the Wallet is the source of truth for balances, assignment 5.1); we do not rebuild them from our transaction history.
- UA: Після рестарту Wallet приймаємо його баланси як є (Wallet є джерелом істини для балансів, завдання 5.1); не відновлюємо їх з нашої історії транзакцій.

- EN: Three identifiers with separate roles: `providerTransactionId` (from the provider) is the idempotency key of WITHDRAW and DEPOSIT and is unique across the system; `transactionId` (ours) identifies every record, CANCEL included, and is sent to the Wallet as `reference`; the Wallet's own dedup key is (operation, `reference`, `betId`). A Cancel has no ID of its own: its key is the `providerTransactionId` of the transaction being cancelled.
- UA: Три ідентифікатори з різними ролями: `providerTransactionId` (від провайдера) є ключем ідемпотентності WITHDRAW і DEPOSIT і унікальний у всій системі; `transactionId` (наш) ідентифікує кожен запис, зокрема CANCEL, і надсилається у Wallet як `reference`; власний ключ дедуплікації Wallet — (операція, `reference`, `betId`). Cancel не має власного ID: його ключ — `providerTransactionId` транзакції, яку скасовують.

- EN: A CANCEL row has provider_transaction_id = NULL and references the cancelled transaction by its provider_transaction_id (storno_transaction_id TEXT UNIQUE REFERENCES transactions (provider_transaction_id)): that is the Cancel's request field, idempotency key and response field (assignment 7.1, 7.4, 8.5). UNIQUE (provider_transaction_id) covers WITHDRAW and DEPOSIT (NULLs are distinct in Postgres), and UNIQUE (storno_transaction_id) allows at most one Cancel per transaction.
- UA: Рядок CANCEL має provider_transaction_id = NULL і посилається на скасовану транзакцію через її provider_transaction_id (storno_transaction_id TEXT UNIQUE REFERENCES transactions (provider_transaction_id)): це поле запиту Cancel, його ключ ідемпотентності і поле відповіді (завдання 7.1, 7.4, 8.5). UNIQUE (provider_transaction_id) покриває WITHDRAW і DEPOSIT (у Postgres NULL не рівні між собою), а UNIQUE (storno_transaction_id) дозволяє не більше одного Cancel на транзакцію.

- EN: The bet row is created together with the WITHDRAW transaction, before the Wallet call, with status NULL; it becomes PLACED only when the withdraw is COMPLETED. This keeps betId stored before the first Wallet call, so every retry sends the same betId.
- UA: Рядок ставки створюється разом із транзакцією WITHDRAW, до виклику Wallet, зі статусом NULL; PLACED він стає лише після COMPLETED withdraw. Так betId збережено до першого виклику Wallet, і кожен повтор надсилає той самий betId.

- EN: Money is shopspring/decimal (exact decimal arithmetic), never float64. The Wallet returns balances as strings with any number of decimals, so integer cents cannot hold them; decimal also reads and writes Postgres NUMERIC. JSON output is a number (MarshalJSONWithoutQuotes = true), as the assignment requires (7, 7.4).
- UA: Гроші представлено типом shopspring/decimal (точна десяткова арифметика), ніколи не float64. Wallet повертає баланси рядками з будь-якою кількістю знаків, тож цілі центи їх не вмістять; decimal також читає і пише NUMERIC у Postgres. У JSON виводиться число (MarshalJSONWithoutQuotes = true), як вимагає завдання (7, 7.4).

- EN: Operations of one player are serialized by a per-player lock, held from the idempotency check until the transaction is updated; different players run in parallel. This makes concurrent identical requests see each other's row (9.2), keeps oldBalance/newBalance consistent and removes races between Withdraw, Deposit and Cancel of the same player (9.6). The cost: a player's requests wait for each other, up to two Wallet calls; waiting is bounded by ctx. The lock is in memory, which is enough for the single api instance in docker compose; with several instances it would move to Postgres (advisory lock). It gives no durability: a PENDING row is committed before every Wallet call (9.1).
- UA: Операції одного гравця серіалізуються локом на гравця, який тримається від перевірки ідемпотентності до оновлення транзакції; різні гравці працюють паралельно. Так однакові одночасні запити бачать рядок один одного (9.2), oldBalance/newBalance лишаються узгодженими і зникають гонки між Withdraw, Deposit і Cancel одного гравця (9.6). Ціна: запити гравця чекають один на одного, до двох викликів Wallet; очікування обмежене ctx. Лок у пам'яті, і цього достатньо для одного екземпляра api у docker compose; якщо екземплярів буде кілька, лок треба перенести в Postgres (advisory lock). Довговічності він не дає: рядок PENDING комітиться перед кожним викликом Wallet (9.1).

- EN: oldBalance is the new_balance of the player's latest non-FAILED transaction in our DB; the Wallet is read only when there is no such transaction or it is PENDING. This avoids an extra call to the unreliable Wallet. If the Wallet's newBalance differs from oldBalance − amount, the balance changed outside our service (e.g. a Wallet restart): this is logged as a warning.
- UA: oldBalance — це new_balance останньої не-FAILED транзакції гравця в нашій БД; Wallet читаємо лише тоді, коли такої транзакції немає або вона PENDING. Так ми уникаємо зайвого виклику ненадійного Wallet. Якщо newBalance від Wallet не дорівнює oldBalance − amount, баланс змінився поза нашим сервісом (наприклад, рестарт Wallet): це логується як попередження.

- EN: On a retry, a Wallet 409 DuplicatedTransaction means the withdraw was applied earlier, but the response has no balance. The transaction becomes COMPLETED with newBalance = oldBalance − amount, where oldBalance was stored before the first attempt. Reading GET /balance instead would return the balance at resolution time, which may already include later operations of the player. The cost: if the balance changed outside our service before the first attempt, this value is not exact.
- UA: Під час повтору 409 DuplicatedTransaction від Wallet означає, що withdraw уже застосовано раніше, але балансу у відповіді немає. Транзакція стає COMPLETED з newBalance = oldBalance − amount, де oldBalance збережено перед першою спробою. Якби ми читали GET /balance, то отримали б баланс на момент розв'язання, який уже може містити пізніші операції гравця. Ціна: якщо баланс змінився поза нашим сервісом до першої спроби, це значення неточне.

- EN: If the Wallet applied a withdraw but the DB update fails, the API answers 202 PENDING rather than 500: that is the state we recorded, and the provider's retry resolves it through the Wallet's 409 DuplicatedTransaction.
- UA: Якщо Wallet застосував withdraw, а оновлення БД не вдалося, API відповідає 202 PENDING, а не 500: саме цей стан ми записали, і повтор провайдера розв'язує його через 409 DuplicatedTransaction від Wallet.

- EN: A retry that resolves a PENDING withdraw to COMPLETED answers 201, not 200: the operation is completed by this request, and there was no completed result to replay.
- UA: Повтор, який переводить PENDING withdraw у COMPLETED, відповідає 201, а не 200: операцію завершено саме цим запитом, і завершеного результату для повтору ще не було.

- EN: A providerTransactionId already used by another player answers 404 NOT_FOUND (the transaction belongs to another player, 7.3), also when two players race and the UNIQUE constraint catches it, so the answer does not depend on who came first.
- UA: providerTransactionId, уже використаний іншим гравцем, дає 404 NOT_FOUND (транзакція належить іншому гравцю, 7.3), зокрема коли двоє гравців змагаються і спрацьовує UNIQUE, тож відповідь не залежить від того, хто встиг першим.

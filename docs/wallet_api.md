# Wallet API: observed behaviour

Observed on `kentechsp/wallet-client:latest` (localhost:8000), 2026-11-16. This is what the mock actually does, not what Swagger says.

All requests need the header `x-api-key`. Error bodies are normally `{"msg": "...", "code": "..."}`.

Setup for the examples: `export WALLET_API_KEY=...` (the key from the assignment - section 5.1), then `H="x-api-key: $WALLET_API_KEY"`

## General behaviour

**Restart:** after `docker restart` the balances return to their initial values and all deduplication keys are forgotten: replaying an old request is applied again.

**Transaction ids:** `id` is one sequence for all users and operations, and restarts from 1 after a Wallet restart; store it for reference only, never as a unique key.

**No bet rules:** the Wallet does not track bets. It accepts a second deposit for the same `betId` and a deposit without any earlier withdraw; `betId` is only a label.

## GET /api/v1/balance/{user_id}

Returns the balance of one wallet user.

**Request:** `user_id` is a 64-bit integer in the path, no body.

**Example**
```bash
curl -s -w '  [%{http_code}]\n' -H "$H" localhost:8000/api/v1/balance/34633089486
```

**Success: 200**
```json
{"balance": "4996.995", "currency": "USD"}
```
`balance` is a **string** (Swagger says number). It can be fractional or very large, so parse it into a decimal type and accept both string and number.

**Errors**

| Situation | HTTP | Body |
|---|---|---|
| Missing or wrong `x-api-key` | 401 | `{"msg":"Authentication error, see logs for more details.","code":"AuthenticatonError"}` (typo is in the Wallet) |
| `user_id` is not a number | 400 | `{"msg":"Request is invalid.","code":"InvalidRequest"}` |
| Wrong route (e.g. extra path segment) | 404 | `404 page not found`, **plain text, not JSON** |
| Internal error | 500 | `{"msg":"Internal server response.","code":"666"}` |
| Connection dropped | no response | empty reply (curl `[000]`) |

**Notes**
- An unknown user is **not** an error: 200 with `{"balance":"0","currency":""}`. It cannot be used to check that a user exists.
- Unreliable: sometimes 500 or a dropped connection, latency up to ~9 s.
- Read only, so retrying is always safe.
- Error bodies are not always JSON, so check the HTTP status first.
- We use it for `oldBalance` before an operation and for `GET /player`. If it fails, never return a stale balance (task section 8.2): answer 502 or 504.

## POST /api/v1/withdraw (bet placement)

Takes money from a wallet user (bet placement, and the compensating call when a deposit is cancelled).

**Request:** headers `x-api-key` and `content-type: application/json`. Body:
```json
{"userId": 34633089486, "currency": "USD",
 "transactions": [{"amount": 1, "betId": 7001, "reference": "w-1"}]}
```
`transactions` is a list, but our API sends one per request. `betId` is an integer generated by us. `reference` is a free string; we put our own `transactionId` there.

**Example**
```bash
curl -s -m 15 -w '  [%{http_code}]\n' -H "$H" -H 'content-type: application/json' -X POST localhost:8000/api/v1/withdraw -d '{"userId":34633089486,"currency":"USD","transactions":[{"amount":1,"betId":7001,"reference":"w-1"}]}'
```

**Success: 200** (Swagger says 201)
```json
{"balance": "4999", "transactions": [{"id": 1, "reference": "w-1"}]}
```
`balance` is the new balance, as a **string**. `id` is the Wallet's integer transaction id (one counter for all operations).

**Errors**

| Situation | HTTP | Body | Applied? |
|---|---|---|---|
| Insufficient funds | 400 | `{"msg":"Insufficient balance for the user.","code":"InsufficientBalance"}` | no |
| Currency differs from the user's | 400 | `{"msg":"Currency mismatch for the user.","code":"InvalidCurrency"}` | no |
| Unknown `userId` | 400 | `{"msg":"User does not exists.","code":"UserNotFound"}` | no |
| Negative amount, empty `transactions` | 400 | `{"msg":"Request is invalid.","code":"InvalidRequest"}` | no |
| Missing or wrong key | 401 | `{"msg":"Authentication error, see logs for more details.","code":"AuthenticatonError"}` | no |
| Same `reference` and `betId` already used for withdraw | 409 | `{"msg":"Transaction already exists.","code":"DuplicatedTransaction"}` | yes, earlier |
| Internal error | 500 | `{"msg":"Internal server response.","code":"666"}` | **unknown** |
| Connection dropped (~5 s) | no response | empty reply (curl `[000]`) | **unknown** |

**Notes**
- **The deduplication key is (operation, `reference`, `betId`).** The same `reference` with another `betId` is a new transaction and is applied. The same pair again gives 409, even from another user or with another amount. Withdraw and deposit are separate (a deposit with the same `reference` and `betId` as a withdraw is applied). Amount and `userId` are not part of the key.
- **A retry must therefore send the same `reference` AND the same `betId`.** Generate `betId` once and store it before the first call, never regenerate it on a retry.
- **A rejected request (400) does not consume the key**: after `InsufficientBalance` the same `reference` and `betId` can still be used. Retrying after a definite FAILED is safe.
- The user is checked before the duplicate: an unknown `userId` gives `UserNotFound` even if the key was already applied.
- **A 500 or a dropped connection says nothing about the outcome**: about 25% of calls fail; behind a failure the operation may have been applied or not (even a 400 can be lost in a dropped connection). Treat them as PENDING, not FAILED.
- **The whole balance cannot be withdrawn**: the amount must be strictly less than the balance. With balance 750.50, withdrawing 750.50 gives `InsufficientBalance`, 750.49 is applied (0.01 left), and then 0.01 gives `InsufficientBalance` again.
- Replaying the same call is always safe. A `409` on replay means "applied earlier", but the response has **no balance**.
- **Gaps in validation** (we must check these before calling the Wallet): more than two decimals is accepted (`1.005`); a zero amount is accepted (200, balance unchanged, an id is consumed); a missing `reference` is accepted and stored as an empty string, which then works like any other `reference` value in the key.
- Latency up to ~9 s.

## POST /api/v1/deposit (bet settlement)

Adds money to a wallet user (bet settlement, and the compensating call of a Cancel). It behaves like withdraw; only the differences are listed in the notes.

**Request:** same headers and body as withdraw.
```json
{"userId": 34673635133, "currency": "USD",
 "transactions": [{"amount": 2, "betId": 9101, "reference": "d-1"}]}
```

**Example**
```bash
curl -s -m 15 -w '  [%{http_code}]\n' -H "$H" -H 'content-type: application/json' -X POST localhost:8000/api/v1/deposit -d '{"userId":34673635133,"currency":"USD","transactions":[{"amount":2,"betId":9101,"reference":"d-1"}]}'
```

**Success: 200** (Swagger says 201)
```json
{"balance": "31417.25", "transactions": [{"id": 1, "reference": "d-1"}]}
```
The balance went from `31415.25` to `31417.25`. `balance` is a string.

**Errors**

| Situation | HTTP | Body | Applied? |
|---|---|---|---|
| Currency differs from the user's | 400 | `{"msg":"Currency mismatch for the user.","code":"InvalidCurrency"}` | no |
| Unknown `userId` | 400 | `{"msg":"User does not exists.","code":"UserNotFound"}` | no |
| Negative amount, empty `transactions` | 400 | `{"msg":"Request is invalid.","code":"InvalidRequest"}` | no |
| Missing or wrong key | 401 | `{"msg":"Authentication error, see logs for more details.","code":"AuthenticatonError"}` | no |
| Same `reference` and `betId` already used for deposit | 409 | `{"msg":"Transaction already exists.","code":"DuplicatedTransaction"}` | yes, earlier |
| Internal error | 500 | `{"msg":"Internal server response.","code":"666"}` | **unknown** |
| Connection dropped (~5 s) | no response | empty reply (curl `[000]`) | **unknown** |

**Notes**
- Same deduplication key, same retry rule and same PENDING handling as withdraw (a 500 or a drop is an unknown outcome).
- There is no `InsufficientBalance`, because money is added.
- Same gaps in validation: a zero amount is accepted (200, balance unchanged, an id is consumed) and more than two decimals is accepted (`1.005` gave balance `31420.255`).
